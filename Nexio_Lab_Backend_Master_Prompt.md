# Мастер-промпт: backend Nexio Lab

Ты senior Laravel-разработчик. Реализуй рабочий backend и админку для сайта Nexio Lab. Существующий React-макет и утверждённый внешний вид сохраняются. Работай в текущем проекте, сначала изучи структуру и существующие контракты, затем реализуй, запусти и проверь результат. Не выдавай прототип за готовый сервис.

## Стек и границы

- PHP и поддерживаемая стабильная версия Laravel; PostgreSQL либо MySQL с поддерживаемой версией, выбранной по среде. SQLite допустим только в локальных тестах. Миграции, seed для демонстрации, очереди по необходимости.
- React-клиент обращается к версионированному JSON API. Зафиксируй OpenAPI или эквивалентную точную схему: маршруты, поля, ошибки, роли, пагинация. Используй единый формат ошибок и даты ISO 8601.
- Админка имеет три основных раздела: CRM, сотрудники, управление сайтом (включая публичные контакты). Новые разделы без необходимости не добавляй.
- Услуги: сайты (лендинги, сайты брендов, маркетплейсы, системы для ресторанов), приложения Android (APK) и Windows. Не предлагай iOS, регистрацию/продажу доменов, серверов или хостинга как отдельные услуги.

## Публичные данные и модели

- Service: slug, название, краткое и подробное описание, обложка, порядок, статус публикации. Seed для направлений «Сайты», «Android», «Windows»; детали веб-направления редактируются в админке.
- Project/Portfolio: slug, заголовок, описание, категория, изображения, ссылки при наличии, порядок, публикация. До внесения реальных работ показывай честное пустое состояние; не выдумывай клиентов или результаты.
- Employee: внутренний ID, неизменный уникальный slug для публичного URL, имя, должность, отдел (IT/продажи), краткое био, полная деятельность, история прихода в компанию, стаж/дата начала при известности, фото, порядок, публичность. Создание сотрудника через админку сразу создаёт запись, доступную по /team/{slug}; отдельные файлы или ручные маршруты для каждого сотрудника не нужны. Смена имени не ломает старую ссылку; при смене slug обеспечь редирект или историю slug. Удаление по умолчанию мягкое.
- Contact/SiteSetting: логотип, слоган «Future Starts Here», вводные тексты, публичный телефон/мессенджеры/email директора, подпись «Работаем онлайн», адрес только если подтверждён. Редактировать через админку, показывать публично.
- Order: внутренний ID, отдельный непредсказуемый публичный идентификатор, клиент и защищённые контактные данные, услуга, описание/бриф, стоимость при согласовании, статус, назначенные сотрудники, сроки, история статусов, даты создания/завершения. Не показывай CRM публично и не делай перебираемый ID средством доступа.
- ClientAccess: одноразовое приглашение или ограниченная по сроку ссылка с криптографически случайным токеном; в БД хранить только хеш, выдачу/отзыв/истечение и аудит. Клиент открывает только свой заказ, подтверждает доступ подходящим способом и заполняет персональный бриф. Повторное использование и перевыпуск регулируются явно. Не клади токены в аналитические события, логи, referer; выставь соответствующие заголовки и редирект при погашении.
- Review: один отзыв от подтверждённого клиента на завершённый заказ согласно согласованной политике, рейтинг и текст, связь с назначенным сотрудником (или компанией), состояние модерации, дата. Публикуй только одобренные отзывы. Не позволяй администратору менять смысл отзыва без следа; хранить историю модерации.
- Media: принимать JPEG/PNG/WebP с реальной проверкой MIME, размера, разрешения и декодирования, случайным именем, обработкой за пределами исполняемых путей. Генерировать оптимизированные размеры и WebP, если обработчик поддерживает; при ошибке преобразования сохранять безопасный исходный JPEG/PNG и показывать его с корректным MIME. Заглушка для сотрудника без фотографии.

## Сценарии и API

1. Публичное чтение: главная, список/детали услуг, проекты, команда/профиль, контакты, опубликованные отзывы. Только опубликованные поля; никаких данных заказов и внутренних заметок.
2. Клиент связывается через опубликованные контакты. Администратор вручную создаёт заказ в CRM и выпускает персональное приглашение. Клиент заполняет бриф по защищённому доступу. Администратор назначает сотрудников и меняет статусы. После завершения клиент получает право оставить отзыв; модерация перед публикацией.
3. CRUD услуг, портфолио, сотрудников, публичных контактов и текстов только после входа с соответствующей ролью. Админка показывает поиск, пагинацию, фильтры, подтверждение опасных действий, историю ключевых изменений.
4. Роли минимум owner/admin и staff с минимально необходимыми правами; доступ к заказам сотрудника задаётся назначением. Все разрешения проверяй на сервере на каждом маршруте и объекте, в том числе при изменении связей и при массовых операциях.

## Безопасность

- Защити вход: надёжные хеши паролей, 2FA для администраторов, безопасные сессии/CSRF для cookie-аутентификации, SameSite/Secure/HttpOnly, строго заданные CORS origins, ограничение попыток и восстановление доступа. Не храни секреты в репозитории.
- Валидация схем и длины полей, параметризованные запросы/ORM, экранирование при выводе, строгая санация допустимого форматированного текста, защита от mass assignment, IDOR и эскалации роли. Никогда не считай знание ID заказа авторизацией.
- Ограничение частоты для входа, приглашений, брифа и отзывов; журнал действий без паролей/токенов/лишних персональных данных; приватная БД, HTTPS, заголовки безопасности, контроль загрузок. Cloudflare/WAF и защита от DDoS настраиваются на инфраструктуре, не объявляй приложение «невзламываемым».
- Автоматические ежедневные резервные копии БД и медиа, внешнее хранение и пробное восстановление. Ротация секретов и обновление зависимостей. Удаление персональных данных по установленному сроку хранения.

## Проверка и поставка

- Тесты: анонимный доступ закрыт; другой клиент не видит чужой заказ даже зная ID; staff не повышает роль; просроченные/повторные ссылки не работают; отзыв возможен лишь после завершения; XSS/SQL-инъекции/поддельный MIME отклоняются; смена slug сохраняет переход; резервная копия восстанавливается.
- Запусти миграции и тесты; опиши результаты и остаточные риски. На собственном стенде проведи ограниченный нагрузочный тест около 50 пользовательских действий в час и короткие контролируемые всплески с метриками latency, ошибок, CPU и RAM. Не направляй DDoS на публичный сервис.
- Подготовь .env.example без секретов, инструкции запуска и деплоя для VPS 2 vCPU/4 GB RAM, миграции, worker, cron, TLS, мониторинг и план отката. Не обещай конкретную вместимость без измерения.
- Критерий готовности: все публичные страницы получают данные из API; админ создаёт сотрудника и его публичная страница открывается по отдельной ссылке; приватный заказ доступен только своему клиенту и уполномоченной команде; отзыв проходит разрешённый цикл; тесты и сборка проходят. Если данных/доступов нет, используй явные демоданные и перечисли, что нужно заменить перед запуском.
